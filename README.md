What is FreeImage ?
-----------------------------------------------------------------------------
FreeImage is an Open Source library project for developers who would like to support popular graphics image formats like PNG, BMP, JPEG, TIFF and others as needed by today's multimedia applications.

FreeImage is easy to use, fast, multithreading safe, and cross-platform (works with Windows, Linux and Mac OS X).

Thanks to it's ANSI C interface, FreeImage is usable in many languages including C, C++, VB, C#, Delphi, Java and also in common scripting languages such as Perl, Python, PHP, TCL, Lua or Ruby.

The library comes in two versions: a binary DLL distribution that can be linked against any WIN32/WIN64 C/C++ compiler and a source distribution.
Workspace files for Microsoft Visual Studio provided, as well as makefiles for Linux, Mac OS X and other systems.

- fixed the RAW plugin not reading a stream that does not start at byte zero. FreeImage_LoadFromHandle reads from wherever the handle stands, so a RAW file may begin part way into a stream that holds something else first; LibRaw_freeimage_datastream measured its size from that point, as it should, but its seek() handed LibRaw's stream-relative offsets straight to seek_proc with SEEK_SET unchanged, so every one of them landed in front of the image. The symptom was worse than a refusal: a DNG carries TIFF magic, so with the RAW plugin unable to recognise it FreeImage_GetFileTypeFromHandle fell through to the TIFF plugin, which validated the file and then failed to load it - the caller got FIF_TIFF and a NULL bitmap instead of the picture, while the same file at offset zero identified as FIF_RAW and loaded, which is why this went unnoticed. seek() now resolves all three origins to an absolute position, offsets SEEK_SET by the stream's start and refuses to move in front of it, since with FreeImage_LoadFromHandle those bytes belong to whoever opened the stream; tell() subtracts the same start. This is the same class of bug fixed earlier in OpenJPEG's stream wrapper, and it predates the LibRaw 0.22.2 upgrade. Covered by TestAPI/RAW's regress at offsets 1, 3, 64 and 1000;
- fixed the RAW plugin's datastream returning the wrong byte on a big-endian machine. LibRaw_freeimage_datastream::get_char() read one byte into an int and returned the int, so the byte landed at whichever end of the int the platform's byte order chose: right on a little-endian machine by accident, shifted left by 24 on a big-endian one. It is not a corner of the plugin - LibRawLite's internal/var_defines.h defines getc() and fgetc() as macros for this method, so the whole of the dcraw-derived decoding reads through it. Counted with the method instrumented, it is called 4 times for each of the uncompressed DNGs in TestAPI/RAW/data, which is LibRaw reading the DNGVersion tag a byte at a time - a big-endian build would not have recognised them as DNGs at all - 7 times for an Olympus ORF, 424 for a Canon CR3, and 4180804 times for a lossless-JPEG-compressed DNG, where it is the bit reader feeding the pixel decoder. It now reads into an unsigned char: one byte, so no byte order is involved, and unsigned because the contract is a value from 0 to 255 or -1 for the end of the stream, and a signed char would return 0xFF as -1 and have it taken for the end of the stream. gets() and scanf_one(), the other two methods that read a byte at a time, already read into char objects and were correct. There is no big-endian machine in this build environment, so this one is by construction; on little-endian everything in TestAPI/RAW and the six real camera files used to check the 0.22.2 upgrade decode to exactly the same bytes as before;

- updated the bundled LibJPEG library to version 10, from the 9d of January 2020, skipping 9e and 9f. The bundle is now byte-for-byte the IJG 10 release of 25-Jan-2026 for every file it carries, minus the build system, the canned jconfig variants for other compilers, the man pages and the test images; the one file that is not upstream's is jconfig.h, which FreeImage writes itself. No patch is carried any more. The old tree had one: jmorecfg.h had been edited to turn `#ifndef HAVE_BOOLEAN` into `#ifdef`, because FreeImage's jconfig.h typedefs boolean itself and sets HAVE_BOOLEAN but, unlike every jconfig upstream ships, did not go on to define TRUE and FALSE - so the library only compiled if that block ran backwards. jconfig.h now defines them the way upstream's own jconfig.txt does, four lines, and jmorecfg.h is pristine. jconfig.h also spells out the four JPEG_*_CUSTOM knobs version 10 adds, all off: the BGR one is tempting for a library whose pixels are BGR, but PluginJPEG.cpp swaps red and blue itself and LibTIFF4, LibRawLite and LibHEIF all expect plain RGB out of libjpeg, so turning it on would quietly corrupt three other plugins. Nothing in the public API moved except two new struct fields (`LSE_maxtrans`, in both the compress and the decompress struct) and JPEG_LIB_VERSION going from 90 to 100, which is why the whole tree has to be rebuilt rather than relinked - none of the makefiles track header dependencies, and a stale object would address the new structs at the old offsets. This is not a security upgrade and is not worth pretending otherwise: the changes IJG made in 9e, 9f and 10 are a data-precision parameter, two jpegtran features, alternate cjpeg/djpeg front ends, and build systems for compilers this tree does not use. The one hardening item, a dimension check in rdgif.c, is in cjpeg's GIF reader, which FreeImage does not build. Decoding does not move: the sixteen files of TestAPI/JPEG/data, all of them coded by 9d, decode to identical bytes through both IDCTs and all seven load flag combinations, as do a JPEG-compressed TIFF and the JPEG payload of a HEIF file; the pristine djpeg binaries of 9d and 10 agree on the same files too, which is the check that does not involve FreeImage at all. LibRawLite, the third library built against these headers, was checked differently: its own three libjpeg call sites (a lossy-JPEG DNG, Kodak raw, and a thumbnail it decodes itself) are not reachable from the four uncompressed DNGs of TestAPI/RAW, and FreeImage's RAW plugin would not use them anyway - it hands a JPEG thumbnail to FreeImage_LoadFromMemory(FIF_JPEG) rather than to LibRaw. What holds for LibRaw is that it compiles against the version 10 headers and that its four files decode identically through both the raw and the preview paths, which is the check the two new struct fields call for. The lossless transforms are byte-identical. Version 10 also rewrote jchuff.c and both DCTs, so the two releases' own cjpeg binaries were run over one image at every quality from 0 to 100 in nine modes: in the seven that write a chrominance table (the four subsampling factors, progressive, optimised Huffman, arithmetic) they agree at exactly the same 25 qualities, the same set each time, and in the two that write none (greyscale, and JCS_RGB, where all three components share one table) they agree at all 101. One table entry accounts for every byte of difference; nothing else in the encoder moved. Encoding moves in exactly one place, and it was 9e that moved it: the sample chrominance quantisation table's DC entry went from 17 to 16 for lossless support. So a greyscale JPEG is byte-identical to what 3.19 wrote, at every quality, there being no chrominance table in the file at all; a colour JPEG is byte-identical at 29 of the 101 quality values - everything from 87 up, 0 to 3 where both clamp to the baseline maximum, and eleven scattered values between - and differs at the other 72, by between 1 and 42 bytes larger on a 256x192 photograph, 0.02% to 0.6%, with the decoded picture moving by at most 2 levels out of 255 at the default quality, and moving towards the original rather than away from it, the finer chrominance step being the more accurate one. TIFF_JPEG saves are unaffected: FreeImage never writes JPEG-compressed TIFF as PHOTOMETRIC_YCBCR, so libtiff gives every component the luminance table and the chrominance one is never written. Regression tests live in TestAPI/JPEG. Not built or tested with MSVC;

Not built or tested with MSVC;
- fixed the G3 plugin hanging on a damaged fax file, and the decode-failure test it never performed. PluginG3.cpp is a copy of libtiff's own fax2tiff tool: it opens a fake write-mode TIFF, points it at the raw file and drives the fax decoder by hand, calling tif_decoderow once per scanline while raw bytes remain. Two things were wrong with that loop. It tested the decoder's return value as `if (!ok)`, but the fax decoders return -1, not 0, when a row cannot be decoded - and -1 is true in C, so the failure branch never ran: a bad line was never counted, never regenerated from the last good one, and simply passed through as if it had decoded. And the loop had no guard against a row that consumes no input, so a decoder that stops making progress spins forever, appending a scanline each time. Upstream fixed both in fax2tiff - the return test in the commit for its issue #191, the progress guard in the one for #759, "avoid endless loop on corrupt input" - and FreeImage's copy predates both; libtiff 4.6.0 had dropped the tools altogether, so there was nothing to notice them in. With the old library the second bug stayed latent, because the decoder always consumed something; 4.7.2 retries a bad line without its EOL marker, which can leave the read pointer where it was, so after this upgrade a truncated and bit-flipped G3 file that used to load in a moment instead ran until memory ran out. The loop now matches upstream's: `ok < 1` for the failure test, and it stops when a row makes no progress or when a Group 4 row fails, that being end-of-block or unrecoverable either way. Row counts on damaged input are bounded by libtiff's own per-strip limit of 8192 bad events, so such a file now yields a large but finite image rather than hanging - a 51-row fax whose tail was corrupted decodes to 8236 rows, the surplus blank, where the old library stopped at 51. Undamaged files are unaffected: a 1728x64 Group 3 fax decodes bit-for-bit identically before and after, and matches the bitmap it was encoded from. Checked under AddressSanitizer over 400 truncation and bit-flip mutations of that file, clean, together with CCITTFAX3 and CCITTFAX4 TIFF round-trips, which are pixel-identical;
