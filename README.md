What is FreeImage ?
-----------------------------------------------------------------------------
FreeImage is an Open Source library project for developers who would like to support popular graphics image formats like PNG, BMP, JPEG, TIFF and others as needed by today's multimedia applications.

FreeImage is easy to use, fast, multithreading safe, and cross-platform (works with Windows, Linux and Mac OS X).

Thanks to it's ANSI C interface, FreeImage is usable in many languages including C, C++, VB, C#, Delphi, Java and also in common scripting languages such as Perl, Python, PHP, TCL, Lua or Ruby.

The library comes in two versions: a binary DLL distribution that can be linked against any WIN32/WIN64 C/C++ compiler and a source distribution.
Workspace files for Microsoft Visual Studio provided, as well as makefiles for Linux, Mac OS X and other systems.

- fixed the RAW plugin not reading a stream that does not start at byte zero. FreeImage_LoadFromHandle reads from wherever the handle stands, so a RAW file may begin part way into a stream that holds something else first; LibRaw_freeimage_datastream measured its size from that point, as it should, but its seek() handed LibRaw's stream-relative offsets straight to seek_proc with SEEK_SET unchanged, so every one of them landed in front of the image. The symptom was worse than a refusal: a DNG carries TIFF magic, so with the RAW plugin unable to recognise it FreeImage_GetFileTypeFromHandle fell through to the TIFF plugin, which validated the file and then failed to load it - the caller got FIF_TIFF and a NULL bitmap instead of the picture, while the same file at offset zero identified as FIF_RAW and loaded, which is why this went unnoticed. seek() now resolves all three origins to an absolute position, offsets SEEK_SET by the stream's start and refuses to move in front of it, since with FreeImage_LoadFromHandle those bytes belong to whoever opened the stream; tell() subtracts the same start. This is the same class of bug fixed earlier in OpenJPEG's stream wrapper, and it predates the LibRaw 0.22.2 upgrade. Covered by TestAPI/RAW's regress at offsets 1, 3, 64 and 1000;
- fixed the RAW plugin's datastream returning the wrong byte on a big-endian machine. LibRaw_freeimage_datastream::get_char() read one byte into an int and returned the int, so the byte landed at whichever end of the int the platform's byte order chose: right on a little-endian machine by accident, shifted left by 24 on a big-endian one. It is not a corner of the plugin - LibRawLite's internal/var_defines.h defines getc() and fgetc() as macros for this method, so the whole of the dcraw-derived decoding reads through it. Counted with the method instrumented, it is called 4 times for each of the uncompressed DNGs in TestAPI/RAW/data, which is LibRaw reading the DNGVersion tag a byte at a time - a big-endian build would not have recognised them as DNGs at all - 7 times for an Olympus ORF, 424 for a Canon CR3, and 4180804 times for a lossless-JPEG-compressed DNG, where it is the bit reader feeding the pixel decoder. It now reads into an unsigned char: one byte, so no byte order is involved, and unsigned because the contract is a value from 0 to 255 or -1 for the end of the stream, and a signed char would return 0xFF as -1 and have it taken for the end of the stream. gets() and scanf_one(), the other two methods that read a byte at a time, already read into char objects and were correct. There is no big-endian machine in this build environment, so this one is by construction; on little-endian everything in TestAPI/RAW and the six real camera files used to check the 0.22.2 upgrade decode to exactly the same bytes as before;

The one hardening item, a dimension check in rdgif.c, is in cjpeg's GIF reader, which FreeImage does not build. Decoding does not move: the sixteen files of TestAPI/JPEG/data, all of them coded by 9d, decode to identical bytes through both IDCTs and all seven load flag combinations, as do a JPEG-compressed TIFF and the JPEG payload of a HEIF file; the pristine djpeg binaries of 9d and 10 agree on the same files too, which is the check that does not involve FreeImage at all. LibRawLite, the third library built against these headers, was checked differently: its own three libjpeg call sites (a lossy-JPEG DNG, Kodak raw, and a thumbnail it decodes itself) are not reachable from the four uncompressed DNGs of TestAPI/RAW, and FreeImage's RAW plugin would not use them anyway - it hands a JPEG thumbnail to FreeImage_LoadFromMemory(FIF_JPEG) rather than to LibRaw. What holds for LibRaw is that it compiles against the version 10 headers and that its four files decode identically through both the raw and the preview paths, which is the check the two new struct fields call for. The lossless transforms are byte-identical. Version 10 also rewrote jchuff.c and both DCTs, so the two releases' own cjpeg binaries were run over one image at every quality from 0 to 100 in nine modes: in the seven that write a chrominance table (the four subsampling factors, progressive, optimised Huffman, arithmetic) they agree at exactly the same 25 qualities, the same set each time, and in the two that write none (greyscale, and JCS_RGB, where all three components share one table) they agree at all 101. One table entry accounts for every byte of difference; nothing else in the encoder moved. Encoding moves in exactly one place, and it was 9e that moved it: the sample chrominance quantisation table's DC entry went from 17 to 16 for lossless support. So a greyscale JPEG is byte-identical to what 3.19 wrote, at every quality, there being no chrominance table in the file at all; a colour JPEG is byte-identical at 29 of the 101 quality values - everything from 87 up, 0 to 3 where both clamp to the baseline maximum, and eleven scattered values between - and differs at the other 72, by between 1 and 42 bytes larger on a 256x192 photograph, 0.02% to 0.6%, with the decoded picture moving by at most 2 levels out of 255 at the default quality, and moving towards the original rather than away from it, the finer chrominance step being the more accurate one. - fixed the G3 plugin hanging on a damaged fax file, and the decode-failure test it never performed. PluginG3.cpp is a copy of libtiff's own fax2tiff tool: it opens a fake write-mode TIFF, points it at the raw file and drives the fax decoder by hand, calling tif_decoderow once per scanline while raw bytes remain. Two things were wrong with that loop. It tested the decoder's return value as `if (!ok)`, but the fax decoders return -1, not 0, when a row cannot be decoded - and -1 is true in C, so the failure branch never ran: a bad line was never counted, never regenerated from the last good one, and simply passed through as if it had decoded. And the loop had no guard against a row that consumes no input, so a decoder that stops making progress spins forever, appending a scanline each time. Upstream fixed both in fax2tiff - the return test in the commit for its issue #191, the progress guard in the one for #759, "avoid endless loop on corrupt input" - and FreeImage's copy predates both; libtiff 4.6.0 had dropped the tools altogether, so there was nothing to notice them in. With the old library the second bug stayed latent, because the decoder always consumed something; 4.7.2 retries a bad line without its EOL marker, which can leave the read pointer where it was, so after this upgrade a truncated and bit-flipped G3 file that used to load in a moment instead ran until memory ran out. The loop now matches upstream's: `ok < 1` for the failure test, and it stops when a row makes no progress or when a Group 4 row fails, that being end-of-block or unrecoverable either way. Row counts on damaged input are bounded by libtiff's own per-strip limit of 8192 bad events, so such a file now yields a large but finite image rather than hanging - a 51-row fax whose tail was corrupted decodes to 8236 rows, the surplus blank, where the old library stopped at 51. Undamaged files are unaffected: a 1728x64 Group 3 fax decodes bit-for-bit identically before and after, and matches the bitmap it was encoded from. Four releases come with it: 1.3 of 18 August 2023, 1.3.1 of 22 January 2024, 1.3.1.2 of 8 December 2025 and 1.3.2 itself, of 17 February 2026. The bundle is byte-for-byte the 1.3.2 release for every file it carries - the fifteen compiled sources and their headers, and zlib's own README, ChangeLog, FAQ, INDEX, LICENSE, manual page, configure, Makefile, Makefile.in and CMakeLists.txt; what it has never carried is the platform directories, contrib, examples, test and doc, and the four templates that configure and CMakeLists.txt generate from - zlib.map, zlib.pc.in, zlib.pc.cmakein and zconf.h.cmakein. The decoder is identical over 1922 cases: 240 whole streams in all three wrappers (raw, zlib and gzip), the same streams truncated at four points each and bit-flipped at three positions each, matching not only in output bytes but in return code and in the error string zlib puts in strm->msg, all six distinct messages the corpus provoked; inflateGetHeader, inflateCopy, inflateReset2 and inflateValidate agree too. Through FreeImage the same holds end to end: 118 output files - PNG at all six flag combinations, TIFF with TIFF_DEFLATE and TIFF_ADOBE_DEFLATE, and the buffers FreeImage_ZLibCompress and FreeImage_ZLibGZip return at fifteen size and content combinations, over eleven source images - are byte-identical to what 1.2.13 produced, and every decoded pixel checksum matches. One thing does move, deflateBound(), in 60 of those 1200 configurations, all of them level 0 with memLevel 9: that is zlib 1.3's "fix bug in deflateBound() for level 0 and memLevel 9", and the new bound is tighter, never once below the size the encoder actually produced. - fixed FreeImage_LockPage() getting slower the further into an animated GIF it went. Reading an n-frame file from beginning to end cost O(n^2), so a few hundred frames took seconds and the last frames of a walk cost fifteen times what the first ones did - the complaint behind issue #18 on the danoli3 fork, whose PR #89 fixes the same two causes on a tree that does not carry this branch's GIF hardening, so the work here is a port of the idea rather than of the patch. The first cause is not specific to GIF: FreeImage_LockPage() opened the plugin's decoder, read one page and closed it again, on every single call. For a GIF that means re-reading every block in the file to rebuild the tables of Graphic Control Extension and Image Descriptor offsets; for TIFF, ICO, AVIF and HEIF, the other paging plugins, it means re-parsing the container. The decoder is now opened by the first FreeImage_LockPage() and kept until FreeImage_CloseMultiBitmap(), which closes it before it saves and before the file handle goes away, since a plugin may still write through that handle. A multi-bitmap created with create_new has no file to open and now returns NULL rather than seeking on a NULL handle. The second cause is the GIF_PLAYBACK compositor. A frame of an animated GIF is only a rectangle to paint over whatever the previous frames left on the logical screen, so to hand out frame n the plugin scanned backwards for the last frame that repaints the whole screen opaquely and replayed forward from there. Optimising encoders write small partial frames, and most of them are transparent, so that scan reaches frame 0 almost always and reading the file in order decoded 1 + 2 + ... + n frames. The plugin now keeps the composited canvas of the frame it last handed out, so the next frame is that canvas with the kept frame's disposal applied and one frame decoded on top; the backward scan still runs for the first frame and after a seek, and seeds the cache on its way out. A second canvas, the one from just before a frame drew its own pixels, is kept only when that frame's disposal method is GIF_DISPOSAL_PREVIOUS, since nothing else is ever restored to it - an ordinary file holds one spare canvas, not two, and pays one memcpy per frame rather than two. Running out of memory for either is not an error: the cache is dropped and the old reconstruction runs, as slowly as it used to. On a 400-frame 320x240 animation with disposal GIF_DISPOSAL_LEAVE, walking every frame goes from 13173 ms to 214 ms, and the per-frame cost stops growing - 0.54 ms whether the file has 50 frames or 400, where it used to be 5.1 ms at 50 and 32.9 ms at 400, and within a single walk of the 400-frame file the last tenth of the frames cost 61.5 ms each against the first tenth's 4.2 ms. GIF_DISPOSAL_BACKGROUND, which the old code could skip decoding but not skip replaying, goes from 338 ms to 215 ms. The extra canvas costs 208 KB of peak RSS on that file. What gets faster is playing an animation forwards and asking for the frame already on screen, which is what a viewer does: over that same 400-frame file, in order 13268 ms becomes 88 ms and the same frame 400 times 294 ms becomes 7 ms. Reading it backwards or at random is not helped at all and is not meant to be - the cache answers the current frame and the one after it, nothing else - so those stay at 13273 and 13278 ms, against 13305 and 13310 after, the 0.2% being the one canvas copy each reconstruction now makes to seed the cache for a forward run that may not come. Nothing about the output moves: fifteen hand-built GIFs - all four disposal methods including the unspecified one, transparency, local palettes, frames with no Graphic Control Extension at all, frames running past the right edge, past the bottom edge and lying entirely off the logical screen, a single frame, two frames, and a sixty-frame mixture - read through eight access patterns each (in order, in order twice, every page twice in a row, backwards, every other page, pseudo-random, and three interleavings) give 2561 results that are byte-identical to the previous library, and every one of them also matches loading that page in a multi-bitmap of its own, where there is no cache to be right or wrong. Clean under AddressSanitizer with leak detection on. The two bounds fixes this branch already carried are what the cached path has to honour as well, and rather than being copied they were moved into the two helpers both paths now call: the horizontal clip that keeps a frame wider than the logical screen from running off the end of a scanline, and the branch that treats a missing Graphic Control Extension as GIF_DISPOSAL_LEAVE instead of reading a disposal method from offset 0. The other paging plugins are unaffected: 65 TIFF, ICO, GIF, AVIF and HEIF files walked forwards, backwards and twice over, opened from a file and from memory, give 1002 identical results, the GIF corpus through the non-playback path gives 19630, and TestAPI's output is byte-identical to what it was before.
