# BMP tests

Standalone programs for the BMP loader's colour masks, alpha, ICC profiles, RLE8
runs and header-only loads, and for what the writer stores. Every file is built in
memory, so the suite carries no data.
Each prints a report and exits non-zero on failure.

| test | what it covers |
|---|---|
| `masks` | 32-bit files: with `BI_RGB` the fourth byte, which the format calls unused, is alpha only when some pixel sets it, so a file holding 0 there loads opaque (40-byte, OS/2 1.x and 2.x headers) and FreeImage's own RGBA saves keep their alpha; with `BI_BITFIELDS` it is alpha only under an alpha mask, from a 56-byte header on (none in a 40- or 52-byte one), and an alpha mask that overlaps a colour counts as none. 32-bit masks in any order and width (R and B swapped, 10-10-10-2, 11-11-10) decode to 8 bits per channel, each value rounded to the nearest. 16-bit: 5-5-5 and 5-6-5 stay 16-bit; other masks become 24-bit, or 32-bit with an alpha mask (4-4-4-4, 1-5-5-5); an alpha mask beyond 16 bits is none. 24-bit `BI_BITFIELDS`, off-spec but written by GIMP 2.10.22 in its V5 headers: its layout stays 24-bit, R and B swapped decode right, and 6-6-6-6 with an alpha mask becomes 32-bit with alpha. `BI_ALPHABITFIELDS`: four masks after a 40-byte header, 16- and 32-bit, bottom-up and top-down; refused at 8 bits. Every case loads header-only (`FIF_LOAD_NOPIXELS`) at the full load's bit depth. A cut file keeps the rows it holds and, without alpha, the rest is opaque; a file cut inside its masks loads blank as 5-5-5. Pixels after a gap: an OS/2 1.x header's 24- and 32-bit pixels are read where `bfOffBits` says. Last, FreeImage's own 32-bit saves: an image whose alpha says something is written with a `BITMAPV5HEADER` (`BI_BITFIELDS`, alpha mask `FF000000`, sRGB, no profile) and loads back unchanged; opaque, never-set (0 everywhere) and CMYK images keep the 40-byte `BI_RGB` header. |
| `icc` | `BITMAPV5HEADER` files with an embedded ICC profile (after the pixels, as in the format): the profile is attached in full and header-only loads, also to a palette image, and one padded in the file is cut to its own size. Not attached, the image loading as usual: a linked profile (a file name, never opened), `sRGB` with profile bytes present, an offset past the file or into the header, a size below an ICC header or of 4 GB, a grey, CMYK or damaged profile, a V4 header. With the display set to sRGB, `FIF_LOAD_DISPLAY_ICC` converts an Adobe RGB file's pixels (or a palette image's palette), exactly as `FreeImage_ApplyDisplayICCProfile()` does, and leaves an sRGB-tagged file's pixels alone. `FreeImage_FIFSupportsICCProfiles(FIF_BMP)` is TRUE. Saves: an RGB profile goes into a `BITMAPV5HEADER` (`PROFILE_EMBEDDED`) after the pixels, as the file's last bytes, at 1, 4, 8 (also RLE8), 16 and 32 bits, and the file loads back with its pixels and profile, header-only too; 16-bit masks sit in the header, none after it; 32-bit images are `BI_BITFIELDS` with an alpha mask only for alpha that says something, so a never-set alpha loads back opaque; a 64 MB profile is kept, one 4 bytes larger left out. Grey, CMYK and damaged profiles, and the profile of a CMYK image, are left out with a warning and the file is written as without one. Images without a profile keep their header: 40 bytes (16-bit: three masks after it), V5 with sRGB for alpha. |
| `rle` | RLE8 literal runs that pass the row end are cut there and the stream is read on past them: 3 pixels past it, 2 past it with the pad byte, a literal starting at the row end; a file cut among the dropped bytes keeps its full row, with a warning. A move past the row end followed by an end of line leaves the next row intact, and 8.4 million moves of 255 pixels on one row (a 34 MB file) end the decoding there instead of carrying the column past 2^31. RLE8 and RLE4 images over 64 MB whose empty rows take no data load with their pixels whatever follows the data (1 or 3 bytes, junk, an ICC profile in a V5 header, which is attached) and without an end of bitmap (an end of line or a move past the last row, or runs that fill it); the same data cut after 600 rows is refused before anything is allocated. RLE8 saves of an image in runs, of one without runs (which RLE8 makes larger than uncompressed) and of a view: `bfSize` is the file's size and `biSizeImage` that of the RLE data, every row's runs fill exactly its width and end the line, the bitmap ends where the file does, and the image loads back unchanged. |
| `save` | `biSizeImage`: pitch x height for 16-bit (`BI_BITFIELDS`) and 32-bit alpha (V5) saves, 0 for `BI_RGB` ones (1, 4, 8, 24, 32-bit). Palette entries are written with `rgbReserved` 0 whatever the dib holds. Row padding is zeros, and so are the unused bits of a 1- or 4-bit row's last byte, for 33-pixel views of parents filled with FF at every bit depth and for plain images with FF in their padding. |
| `nopixels` | A header-only load (`FIF_LOAD_NOPIXELS`) describes what the full load returns: for 12-, 40-, 56-, 64- and 124-byte headers, every bit depth from 1 to 64 and compressions 0 to 6 and 11 to 13, both loads refuse the file or give the same size, bit depth, palette size and masks. A 1-, 4- or 8-bit image with a compression its depth cannot use (RLE8 below 8 bits, RLE4 at 1 or 8 bits, compression 3, which OS/2 uses for Huffman 1D), and a 16-, 24- or 32-bit one with RLE4 or RLE8, is refused by both, under the Windows and the OS/2 2.x header. 24-bit compression 3 loads under a 40-byte header (masks) and is refused under an OS/2 2.x one (Huffman 1D). |

## Running

Build the library first (`make -f Makefile.gnu dist` in the repo root), then:

    make run        # masks, icc, rle, save, nopixels
    make asan-run   # all five, with PluginBMP.cpp rebuilt with AddressSanitizer and UBSan

## What "expected" looks like

Every line `ok` and `--- 0 failure(s) ---`. On Windows the programs build with
`zig cc -target x86_64-windows-gnu` or MSVC against the static library.
